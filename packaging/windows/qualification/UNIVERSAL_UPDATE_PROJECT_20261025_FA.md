# پروژه UUP-01 — انتشار و به‌روزرسانی واحد سکنا

**وضعیت:** اجرای مهندسی، بدون مجوز نصب عمومی تا عبور از گیت میزبان واقعی. ۲۵ اکتبر ۲۰۲۶

## هدف غیرقابل مذاکره
- برای هر مؤلفه (Local / Public / Windows Services) و نسخه مقصد **یک بسته واحد** منتشر شود، نه بسته به نام خانه یا کافه.
- همان ZIP بدون تغییر محتوا روی هر نصب **سازگار و فهرست‌شده** کار کند، حتی اگر نسخه‌های فعلی متفاوت باشند.
- کار اپراتور فقط «انتخاب ZIP → بررسی خودکار → نصب → مشاهده نتیجه» باشد. کلید، PowerShell، EXE، اصلاح هویت دستگاه، مسیر نصب و دیتابیس در روند معمول ممنوع.
- تشخیص installed release/tree/schema/migration به‌صورت runtime، نه نام میزبان؛ عدم‌سازگاری به‌صورت fail closed *قبل از تغییر* با پیام دقیق.
- Local، Public، Maintenance و Windows Services مستقل منتشر شوند؛ وابستگی واقعی پیش از نصب تعیین شود.
- هیچ Downgrade یا بازنویسی Migration قبلی، خاموش‌کردن امضا یا جعل گواهی آزمون مجاز نیست.

## معماری حداقلی و انتخاب‌های فنی

**برای Local:** موتور فعلی Release Set v2.1 فایل `web-tree-zip-v1` (تصویر کامل اسلات) را می‌پذیرد. بسته باید شامل `targets.local` و `supported_baselines` دقیق برای نسخه‌های واجد شرایط باشد. ناشر از ۱ تا ۶۴ baseline دقیق پشتیبانی دارد. واحد بودن بسته به معنی «پذیرش همه نسخه‌های تاریخ بدون صلاحیت» نیست؛ نسخهٔ خارج از دامنه یا خراب باید رد شود و یک مسیر ارتقای ایمن/ریکاوری مستقل دریافت کند.

**اندازه:** با موتور فعال فعلی، Full Snapshot گزینهٔ امن است. Delta *فقط اگر* استیج در اسلات غیرفعال با بازسازی snapshot کامل و مقایسهٔ هش نهایی انجام شود، و هنگام اختلال بازگشت/بازیابی آزمون شود. استفاده از Delta به‌شکل کپی روی اسلات فعال ممنوع است. تا زمان اثبات آن، افزایش چند مگابایتی پذیرفته می‌شود؛ ساده‌سازی حجم نباید مانع ایمنی نصب شود.

**برای Public:** قرارداد بستهٔ Public جدا است؛ ناشر و پنل باید سازگاری با نسخهٔ Local و Public فعلی را بررسی کنند. ادعای یونیورسال Local را نمی‌توان بدون تست به Public تعمیم داد.

**Migration:** fingerprint واقعی از کاتالوگِ بدون تغییر محاسبه شود. مهاجرت‌ها فقط روبه‌جلو و به‌صورت idempotent/ledger اجرا شوند. بعد از مرز دیتابیس، عقب‌گرد کد فقط با اثبات سازگاری یا بازیابی رو به جلو؛ هرگز rollback کور دیتابیس.

**امضای انتشار:** ابزار ناشر از P256 موجود استفاده می‌کند و به کلید خصوصی محافظت‌شده و گواهی واقعی آزمون نیاز دارد. بستهٔ آزمایشی بدون امضا نباید install-qualified شود. نباید کلید را از ZIP وارد trust store کرد و نباید کلید خصوصی را به خانه/کافه منتقل کرد.

| P1 ناشر واحد | گیت چند baseline، کشف خودکار fingerprint و manifest، بازخورد روشن | پیاده‌سازی اولیه | همهٔ تست‌های منفی و مثبت و CI روی شاخه مستقل موفق |

## وضعیت کاندیدای R5
- ZIP قبلی R5 با یک baseline (231BO)، `production_pass=false`، بدون امضا و بدون fingerprint مقصد بود؛ **قابل انتشار نبوده است**.
- ابزار `universal_release_prep.py` هدف 231BP را از همان payload بدون تغییر ساخته و از آرشیوهای معتبر تاریخی ۳ مشخصهٔ دقیق 231BL، 231BN و 231BO را استخراج کرده؛ هدف schema fingerprint و مسیر migration 0076 را محاسبه کرده است.
- خروجیِ فعلی **SOURCE_PREPARATION_NOT_INSTALLABLE** است؛ این وضعیت عمدی است و جایگزین امضا/نصب واقعی نیست.
- نسخه‌های فرضی 231AC و 231BA صرفاً مثال هستند؛ تا وقتی هویت دقیق آن‌ها از سوابق تأییدشده بازیابی نشده، در allowlist قرار نمی‌گیرند.

## هر نسخهٔ بعدی چگونه منتشر می‌شود؟
1. ناشر با دریافت snapshot مقصد و فهرست نسخه‌های مبنای تاییدشده، همان یک بستهٔ مقصد را می‌سازد.
2. CI به‌صورت خودکار هش‌ها، migration plan، تست‌های متناسب با تغییر و منفی‌های بسته را اجرا می‌کند.
3. در مرحله محافظت‌شده، فقط پس از دریافت شواهد معتبرِ تست واقعی، بسته امضا و منتشر می‌شود.
4. اپراتور ZIP را در پنل انتخاب می‌کند؛ روی هر دستگاه وضعیت خودش بررسی می‌شود. در صورت ناسازگاری، نصب آغاز نمی‌شود و علت/راه‌حل روشن نمایش داده می‌شود.
5. پس از نصب، نتیجه در پنل و Support Bundle ثبت می‌شود تا برای عیب‌یابی به فایل جانبی نیاز نباشد.

## امور به‌طور مشخص ممنوع
- ایجاد بستهٔ خاص کامپیوتر، کلید اختصاصی کافه در ZIP، کنارگذاشتن امضا/گیت‌ها، ثبت PASS ساختگی، انتشار Main یا Release بدون UAT، اعمال وصله روی فایل فعال.
