# آیا بسته Public از کارخانه انتشار ساخته شده؟ — گزارش R265/R266

**تاریخ:** ۱۷ نوامبر ۲۰۲۶  
**نتیجه:** خروجی‌های R265 و R266 **خارج از Workflow یکپارچه انتشار R233** ساخته و از مسیر اختصاصی R267/R268 آزمایش شده‌اند.

## منشأ واقعی

| مؤلفه | مسیر واقعی | وضعیت |
|---|---|---|
| بسته اول | R265 / 35if / `692aa40939d788aea56efa4e3b62c46a568da0ce5c508cc87844aa63366b8892` | Bridge کد-only؛ ۸ Migration؛ QA |
| بسته دوم | R266 / 35ig / `b6d4d2236ab3da126a4070d75802a9cac6719c139a188808d1712b8c1827bd35` | ارتقای ۸→۱۱ Migration؛ QA |
| سازنده | `r267/build_qa_packages.py` | مخصوص مبدأ `35ic/R249` و بازیابی Emergency قدیمی |
| CI مبدأ | [R268 / Run 44025587468](https://github.com/mobaraki20/SoknaCafeV3/actions/runs/44025587468) | HTTP، PHP 8.3، MariaDB 11.4؛ پاس |
| کارخانه یکپارچه | [SOKNA Unified Release Factory](https://github.com/mobaraki20/SoknaCafeV3/actions/workflows/sokna-release-factory.yml) | **برای این دو ZIP استفاده نشده است**؛ فعلاً فقط R233 |
| نصب روی هاست و بازیابی بکاپ | گزارش زنده ندارد | NOT_RUN، Production BLOCKED |

در خروجی R268، دو نام جدیدِ دارای شمارهٔ 01/02 ممکن است برای تحویل به اپراتور آمده باشند، اما **بایت و SHA بسته‌های داخلی دقیقاً همان دو ZIP آزمایش‌شده هستند**. تغییر نام به‌خودی‌خود تأیید نصب نمی‌سازد. Manifest داخلی هم هنوز عمداً provenance مربوط به QA را حفظ کرده است.

## تجربه‌هایی که باید وارد کارخانه شوند

۱. **قابلیت واقعی نسخه مبدأ Emergency را بپرس، نه فقط VERSION را.** در نسل `35ic`، Emergency قدیمی تغییر Schema را موقع Activate رد می‌کند (`emergency_schema_mutation_not_qualified`)؛ پس R262 را مستقیم Activate نکن.

۲. **استثنای سازگاری را از قاعده عمومی جدا کن.** فقط برای این مبدأ قدیمی، ابتدا R265 / `35if` با همان ۸ Migration و Commit و Readback؛ سپس R266 / `35ig` با ۱۱ Migration و Commit لازم است. قاعده عمومی پابلیک همچنان «یک ZIP یکسان برای Routine و Emergency **هر نسخه**» است، نه اینکه همه نسخه‌ها از این پس دو ZIP داشته باشند.

۳. **آزمون واقعی مسیر HTTP نصب:** نام فایل، Login، CSRF، Upload، Stage/Activate/Commit **در درخواست‌های جداگانه**، Health، حفظ فایل‌های protected و دیتابیس باید در همان سناریوی واقعی بررسی شوند؛ فقط فراخوانی مستقیم PHP کافی نیست.

۴. **مرز DB-forward را صریح علامت بزن:** بعد از Migration رو‌به‌جلو، برگشت به کد قبلی می‌تواند مخرب باشد؛ تست خطای وسط DDL و Resume باید با همان نسخه انجام شود. وضعیت backup خارج از host و restore readback جدا از سبزبودن CI است.

۵. **جابه‌جایی Public را از Update جدا نگه دار:** Local مرجع سفارش و منوست؛ Public جایگزین نباید سفارش مهمان باز/معلق داشته باشد. پس از سلامت Public، باید Pairing مالک‌ها، انتقال منو و تصاویر، سفارش مهمان آزمایشی و QR قدیمی بررسی شوند. نیازی به انتقال دادهٔ صرفاً Public قدیمی به مقصد جدید نیست.

۶. **بدون امضای میدانی، QA را Release جا نزن:** حتی با دو ZIP بایت‌به‌بایت تأییدشده، SHA فایل‌های محافظت‌شدهٔ میزبان، backup/restore، Health پس از هر مرحله و تأیید اپراتور لازم است.

## از این پس گزارش هر خروجی Public باید چه داشته باشد؟

خروجی هر بسته (در همان پیام تحویل و کنار لینک دانلود) باید صریح و بدون نیاز به پرسیدن این فیلدها را گزارش کند:

| فیلد اجباری | مثال فعلی |
|---|---|
| **Factory used?** | **NO — External R268 QA builder** |
| Producer workflow + Run | `SOKNA R268 Real HTTP Emergency Release Qualification` / `44025587468` |
| Source + exact baseline | `R249 / 35ic` با Managed Tree SHA ثبت‌شده |
| SHA همان ZIP تحویلی | SHA دقیق هر دو فایل بالا |
| QA / Database / HTTP | PASS فقط در آزمون ایزوله |
| Field install / backup/restore | NOT_RUN / PENDING |
| Final operator status | BLOCKED (تایید نشده برای نصب معمول) |

**سازوکار فعلی GitHub به‌صورت خودکار تمام شاخه‌های QA دیگر را تحت پوشش نمی‌گیرد.** اگر یک ایجنت در چت دیگر با Workflow جداگانه خروجی ساخت، باید آن را به درگاه انتساب منشأ وصل کند. در غیر این صورت «Factory used: NO یا UNKNOWN» گزارش شود؛ نه اینکه از سبزبودن CI نتیجه گرفته شود کارخانه استفاده شده است.

## سازوکار ثبت منشأ R268

`release-ops/external-public-r268-provenance.json` منبع، Run و SHA را پین می‌کند. `release-ops/trace_external_public_candidate.py` خود ZIPهای تولیدکننده را بررسی می‌کند، و `.github/workflows/sokna-r268-candidate-attribution.yml` فقط گزارش «Factory NOT USED» را با دلایل و وضعیت واقعی منتشر می‌کند؛ **هیچ تغییری در سورس یا دو ZIP موجود نمی‌دهد**.

برای نسخه بعدی، یا سازنده واقعاً از مسیر `sokna-release-factory.yml` عبور کرده و Run ID مربوط به همان ZIP را ارائه کند، یا گزارش منشأ خارجی داشته باشد و تا تکمیل گیت‌های مرتبط، منتشرشده/پذیرفته‌شده تلقی نشود. این شفافیت به معنای تمام‌شدن تبدیل کارخانه R233 به یک سازنده عمومی نیست.


## نکته تازه از بازرسی مستقیم ZIP: فایل‌های Recovery

در بازخوانی بایت‌های واقعی R249، R265 و R266 معلوم شد `recovery.php` و `src/Recovery/StableRecoveryService.php` در هر سه payload مدیریت‌شده حضور دارند و **SHA آنها دقیقاً یکسان است**. بنابراین قانون صحیح برای این دو فایل «حفظ بایت‌های کد Recovery از مبنای قبلی» است، نه «حذف کامل از هر ZIP به دلیل حساس‌بودن». این موضوع با فایل‌های واقعاً مستقلِ `emergency.php`، `src/Emergency/**` و کلیدهای میزبان فرق دارد.

درگاه جدید این دو SHA تاریخی را کنترل می‌کند؛ حذف یا تغییرشان را به همان اندازه ورود فایل‌های پیکربندی محرمانه رد می‌کند. این آزمون به‌تنهایی اثبات نصب/بازیابی پس از قطع سرور نیست.


## محدودیت نگهداری شاهد GitHub

آرشیو Actions مربوط به اجرای R268 با **نگهداری ۷روزه** ساخته شده است. آزمون بازخوانی خود ZIP تا زمان اعتبار آن قابل بازاجراست؛ پس از انقضای Artifact نباید به‌اشتباه ادعا کنیم بایت‌های فایل از GitHub دوباره تأیید شده‌اند. گزارش SHA و Manifest و این مستند در Git حفظ می‌شود؛ نسخه فایل‌های تحویلی در Workspace/Library نگهداری شده‌اند. آزمون تاریخی نباید شرط دائم تمام PRهای بعدی شود یا بدون منبع جایگزین معتبر به‌صورت خودکار PASS اعلام شود.
