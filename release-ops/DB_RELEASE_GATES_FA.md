# کنترل پایگاه داده در مسیر انتشار سکنا — ۱۶ نوامبر ۲۰۲۶

**محدوده:** زیرساخت GitHub و دیتابیس‌های موقت MariaDB 11.4. هیچ تغییری در دیتابیس کافه، سورس Local/Public، ابزار Windows/Maintenance یا بسته عملیاتی داده نشده است.

## چرا لازم است؟
هم‌تعداد بودن Migrationها دلیل سازگاری دیتابیس نیست. لازم است تک‌تک SQLهایی که در نسخه‌های نصب‌شده اعمال شده‌اند از نظر مسیر، ترتیب و SHA256 با نسخه مقصد تطبیق داده شوند؛ همچنین قبل از تعویض کد باید از داده موجود بکاپ معتبر گرفته شود و آزمون بازیابی جداگانه انجام شود. بعد از عبور از مرز DB-forward، rollback خودکار کد بدون قواعد Recovery مجاز نیست.

## ابزارهای جدید در GitHub
- `release-ops/db_gate.py`: با سورس ZIP کامل و آرشیو مبنای دقیق، نام و هش تمام Migrationهای قبلی را می‌سنجد، حذف/تغییر/جابه‌جایی فایل‌های اجراشده را رد می‌کند و Migration جدیدِ دارای SQL تخریبی را متوقف می‌کند. این یک کنترل **فقط‌خواندنی** است.
- `release-ops/qa_db_roundtrip.php`: فقط با `GITHUB_ACTIONS=true` و `SOKNA_RELEASE_DB_QA_DISPOSABLE=YES` و نام‌های ثابت دیتابیس آزمایشی اجرا می‌شود؛ از تمام ردیف‌های همه جدول‌ها اثرانگشت منطقی می‌گیرد، داده آزمایشی نگه می‌دارد و اجرای مجدد Migrationهای Local را کنترل می‌کند.
- `.github/workflows/sokna-release-db-gate.yml`: MariaDB 11.4 موقت، Setup واقعی با کد تغییرنیافته R233، منطق ذخیره تنظیمات و حساب کاربری، بکاپ consistent با `mariadb-dump --single-transaction`، بازیابی در دو دیتابیس جدید و تطبیق محتوای تمام جدول‌ها. به‌عنوان Workflow مستقل و نیز از مسیر QA بسته‌ها فراخوانی می‌شود.
- `release-ops/tests/test_db_gate.py`: آزمون‌های منفی حذف، تغییر، تقدم/ترتیب و SQL تخریبی Migration، خطای SHA آرشیو مبنا و موارد بدون شاهد.

## مرز ادعاهای این آزمون
- اجرای مجدد Migration از **مالک نصب مستقل Public** هنوز `NOT_RUN` است؛ صرف Boot یا تطبیق ۸ SQL جای آن را نمی‌گیرد.
- ارتقای دیتابیس‌های **نصب واقعی قدیمی** با هویت Full/Delta، انواع داده قدیمی و خطای میانهٔ مهاجرت `NOT_RUN` است.
- اجرای Backup/Restore در هاست واقعی، قفل‌بودن فایل‌ها، مجوزهای Windows، مرز DB-forward و سناریوی بازیابی بعد از فعال‌سازی `NOT_RUN` است.
- این آزمون هیچ اثباتی درباره همگام‌سازی داده عملیاتی بین Local/Public یا حفظ پرونده‌های ۲۷گانه HOLD ایجاد نمی‌کند.
- هیچ خروجی سبز به‌تنهایی به معنی «نصب‌پذیر در کافه» یا مجوز استفاده از `production_pass=true` نیست.

## فرآیند ساده برای هر نسخه بعدی
۱) ایجنت قبل از هر انتشار، آخرین سورس معتبر Library را با `release-ops/active-source.json` و دفتر SHA تطبیق می‌دهد؛ اگر نسخه جدیدتری تصویب شده باشد، مرجع را با شواهد واقعی به‌روز می‌کند. نام شاخه GitHub یا `VERSION.txt` منبع حقیقت نیست.
۲) `sokna-release-source-intake.yml` سورس دقیق را از GitHub پیدا می‌کند و درگاه DB Static را اجرا می‌کند. قالب واقعی بسته براساس مالک نصب انتخاب می‌شود، نه براساس نام فایل ZIP.
۳) سازنده موجود بسته QA را تولید می‌کند؛ `source_gate.py` و `audit.py` و دفتر عدم برخورد نسخه روی بایت‌های نهایی اجرا می‌شوند.
۴) برای Release واقعی، آزمون نصب، دیتابیس، بکاپ و بازیابی با همان SHA بسته در Windows Maintenance یا هاست Public انجام می‌شود و گزارش `PASS/FAIL/NOT_RUN` می‌دهد.
۵) تا زمانی که شواهد واقعی باقی‌مانده تکمیل نشده، فقط خروجی QA/DO-NOT-INSTALL مجاز است.
