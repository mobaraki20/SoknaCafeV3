## چرا با وجود این همه کار همچنان ابهام باقی مانده بود؟

- برنامه‌های R269 تا R278 در شاخه‌های QA بلندمدت منشعب شده‌اند. چند شاخه حتی **AGENTS.md مربوط به سیاست کارخانه را ندارند**، چون کد کارخانه در `main` به‌روزرسانی شد ولی این شاخه‌ها از `main` به‌روزرسانی نشده‌اند.
- GitHub به‌صورت خودکار هر Workflow موجود یا ZIP خروجی از Library را از کارخانه عبور نمی‌دهد؛ هر سازنده باید آن را فراخوانی کند.
- حتی وجود فایل `for_install=true`، بدون رسید نهایی، تأیید اصل سورس و آزمون میزبان واقعی، به معنای صدور مجوز عملیاتی نیست.
- **قانون branch protection / required check برای منع تمام انتشارهای خارج از کارخانه، با ابزارهای موجود این مکالمه تنظیم نشده است.** نباید وانمود کنیم اجرای مستقل خارج از GitHub Actions یا در چت دیگری خودکار متوقف می‌شود.

## قانون لازم‌الاجرا برای همه ایجنت‌ها و تحویل بسته

۱. ابتدا Source authority آخرین Workspace، تصمیم‌های ACCEPT/HOLD و نسخه/شمای مبنا را به‌صورت دقیق بررسی کن؛ آخرین نام شاخه را مساوی سورس نهایی فرض نکن.

۲. بعد از تولید ZIP با بسته‌ساز واقعی، آن را در همان اجرای GitHub Actions به Artifact اصلی اضافه کن. پس از محاسبه SHA واقعی، Manifest `candidate-contract.json` تولید کن، و `sokna-release-factory.yml@main` را با `track=registered-candidate` به‌عنوان Job وابسته **الزامی** فراخوانی کن. سازندهٔ جدید یا Checkout جداگانه از نسخهٔ آزمایشی دیگر نساز.

۳. بستهٔ قابل ارائه باید **رسید نهایی همان ZIP** را داشته باشد: Producer Run ID، Factory Run ID، نام ZIP، SHA، نسخه، مبنا، Source validation، DB-forward، Windows/HTTP QA، Backup/Restore، پذیرش میدانی و تصمیم. هر فیلد بدون شاهد `NOT_RUN` است، نه PASS.

۴. اگر رسید وجود ندارد، برچسب آن `NO_FACTORY_RECEIPT_VERIFIED` است؛ از اصطلاح «خروجی رسمی»، «از کارخانه گذشته» یا «تأیید نصب» استفاده نکن. ساختن ZIP آزمایشی برای تشخیص خطا ممنوع نیست، **تحویل آن به‌عنوان Release تأییدشده ممنوع است**.

۵. تا تنظیم حفاظت شاخه توسط مدیر مخزن و انتقال همه سازنده‌ها به گیت مشترک، نمی‌توان در سطح سرور تضمین کرد هیچ شخص یا چت دیگری مسیری خارج از این استاندارد طی نکند. از نظر عملی، هر عامل باید نبود رسید را **وقفهٔ انتشار** بداند، نه یک هشدار قابل چشم‌پوشی.
