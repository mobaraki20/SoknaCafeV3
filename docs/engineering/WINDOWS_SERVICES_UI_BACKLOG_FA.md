# Backlog اجباری UI برای Windows Services

این سند یک backlog دائمی برای Installer / Dashboard سرویس‌های ویندوز سکنا است.

**Baseline مشاهده‌شده:** Windows Services 1.0.11

هدف این سند این است که اگر در آینده Windows Services به هر دلیل دیگری اصلاح، بازسازی یا نسخه جدیدی از آن منتشر شد، موارد زیر فراموش نشوند و در همان چرخه اصلاح/qualification قرار بگیرند. این موارد به‌تنهایی الزام به ساخت نسخه جدید فوری ایجاد نمی‌کنند؛ اما در اولین تغییر بعدی این Installer باید بررسی و بسته شوند.

## موارد اجباری برای اولین اصلاح بعدی

1. **تناقض وضعیت Footer در حالت Upgrade**
   - وقتی نسخه نصب‌شده قدیمی‌تر است و Dashboard وضعیت «به‌روزرسانی آماده است» نشان می‌دهد، footer نباید همزمان «وضعیت به‌روز است» نمایش دهد.
   - متن footer باید از همان state machine اصلی تغذیه شود و با Fresh / Current / Upgrade / Repair / Partial هماهنگ باشد.

2. **تفکیک روشن نسخه برنامه مدیریت از نسخه سرویس‌های نصب‌شده**
   - badge یا عنوان بالای Dashboard باید صریحاً مشخص کند که مثلاً `1.0.11` نسخه خود برنامه مدیریت/Setup UI است.
   - در کارت وضعیت باید جداگانه «نسخه سرویس‌های نصب‌شده» نمایش داده شود.
   - در حالت Upgrade نباید کاربر بین نسخه برنامه و نسخه سرویس‌ها سردرگم شود.

3. **بهبود UX حالت Connected / Pairing**
   - وقتی Local Web از قبل متصل است، صفحه نباید دائماً شبیه فرم Pairing خام باشد.
   - در حالت Connected ابتدا وضعیت اتصال و آدرس Local Web به‌شکل خوانا نمایش داده شود.
   - فیلد «کد اتصال» فقط زمانی نمایش/فعال شود که کاربر action مشخص «نوسازی اتصال» یا «اتصال مجدد» را انتخاب کند.
   - Pairing همچنان lifecycle مستقل بماند و reinstall سرویس‌ها انجام نشود.

4. **اصلاح کنتراست دکمه «نوسازی اتصال»**
   - متن و پس‌زمینه باید WCAG-like contrast مناسب برای خوانایی داشته باشند.
   - دکمه primary روی زمینه سبز نباید متن تیره و کم‌کنتراست داشته باشد؛ متن سفید/کنتراست مناسب ترجیح داده شود.

5. **کاهش جزئیات فنی از نمای اصلی**
   - رشته کامل `Visual C++` و شماره build آن در نمای اصلی ضروری نیست.
   - در Dashboard اصلی کافی است «پیش‌نیاز ویندوز آماده است» نمایش داده شود.
   - نسخه دقیق Visual C++ و سایر جزئیات فنی به «جزئیات» یا مرکز عیب‌یابی منتقل شوند.

## الزامات Qualification همراه این اصلاحات

- screenshot واقعی حداقل در `960x600`, `1100x660`, `1280x720` بازبینی شود.
- برای stateهای Current و Upgrade screenshot جداگانه وجود داشته باشد.
- footer status با state machine تست شود تا تناقض متنی ممکن نباشد.
- label نسخه برنامه و نسخه سرویس‌های نصب‌شده به‌صورت مجزا در تست UI/assertion بررسی شوند.
- حالت Connected نباید فیلد خالی Pairing را به‌صورت پیش‌فرض به کاربر تحمیل کند.
- دکمه‌های primary باید text clipping و contrast قابل قبول داشته باشند.

## قاعده اجرایی

در اولین تغییر بعدی `packaging/windows` که منجر به candidate جدید می‌شود، این سند باید قبل از qualification مرور شود. هر مورد یا باید بسته شود، یا اگر عمداً defer شد دلیل آن در release notes همان نسخه ثبت شود.
