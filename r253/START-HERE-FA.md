# R253 — چک‌پوینت ادامهٔ موتور یونیورسال انتقال سکنا
**تاریخ:** ۱۶ نوامبر ۲۰۲۶  
**شاخهٔ QA:** `qa/sokna-r253-migration-approval-ledger-20261116`  
**شاخهٔ قبل:** `qa/sokna-r252-universal-identity-attestation-20261116`

## هدف
موتور **یونیورسال، مستقل از نام مشتری، دامنه، نسخه، محل نصب و نوع هاست** برای انتقال Public یا Local؛ رابط بسیار ساده برای مدیر یک کافهٔ کوچک. هیچ کدام از آدرس‌های واقعی گذشته پیش‌فرض کد نیستند؛ صرفاً سناریوی رگرسیون‌اند. هر نصب متعلق به مالک مستقل خود است و تأیید مشتری دیگر را نمی‌پذیرد.

## قبل از شروع چت بعدی
به ترتیب این فایل‌ها را بخوان:
1. `r251/DECISIONS-FA.md`، `r251/decisions.json` (تصمیم‌های فعال MIG-001 تا MIG-013 و قبلی‌های OLD-* منسوخ).
2. همین `r253/START-HERE-FA.md` و `r253/STATUS.json`.
3. `r252/START-HERE-FA.md` و `r252/SECURITY-BOUNDARY-FA.md`.
4. کدهای `PublicMoveDecisionEngine.php`, `PublicMoveIdentityVerifier.php`, `PublicMoveApprovalMac.php`, `PublicMoveApprovalLedger.php`.
5. تست `r253/test-public-move-approval-ledger.php` و SQL آزمایشی `r253/approval-ledger-schema-fixture.sql`.
6. آخرین CI فایل `.github/workflows/sokna-r253-public-move-ledger.yml`.

## وضعیت اجرای واقعی
- **R251:** ۵۵ آزمون کشف مقصد/چندمشتری موفق.
- **R252:** ۵۷ آزمون امضای Ed25519 و grant مبتنی بر MAC (Local-only) موفق؛ هنوز endpoint احراز مالک واقعی تولید نشده.
- **R253:** کلاس `PublicMoveApprovalLedger` برای ثبت تراکنشی درخواست، قفل یک عملیات فعال در هر Local، ذخیرهٔ hash challenge، تأیید cryptographic و ثبت receipt، انقضا و مصرف یک‌بارهٔ nonce. SQL همراه آن فقط fixture است.
- **گیت واقعی MariaDB 11.4:** GitHub Actions `43767627807` موفق. همچنین تست‌های R251/R252 و دفتر تصمیم‌ها اجرا شده‌اند.
- هیچ فایل نصب روی سیستم کافه، هاست پابلیک، `main`، `CURRENT` یا دیتابیس‌های واقعی تغییر نکرده است.
- این مرحله فقط مجوز لازم برای **پیش‌بررسی** را پایدار ثبت می‌کند؛ `safe_to_cutover=false` و فعال‌سازی Public/انتقال داده هنوز مطلقاً مجاز نیست.

## محدودیت‌های موجود (شفاف)
- تأیید واقعی مدیر مقصد، مدیریت نشست/CSRF و مجوزها در UI و API.
- تولید و نگهداری کلیدهای هر نصب در محل محافظت‌شده.
- تطبیق fixture جدول‌های جدید با migration شماره‌گذاری‌شدهٔ واقعی Local؛ SQL این مرحله **به نصب زنده منتقل نشود**.
- ارزیابی هم‌زمانی با دو worker واقعی/قطعی و recovery پس از claim در E2E.
- اتصال probe عمومیِ read-only به Local و Public، هماهنگ‌سازی سفارش‌های معلق، کنترل authority epoch و guardهای cutover.
- رابط کوتاه «آدرس → تأیید مالکیت → نتیجه»، آزمون روی دستگاه/هاست واقعی و ساخت بستهٔ تجمیعی.

## قدم بعدی دقیق و ثابت
۱) طراحی endpoint تأیید مقصد از نشست مدیر احرازشده و اتصال امن آن به grant؛ اطلاعات مرورگر به‌تنهایی اعتمادآور نیست.  
۲) تأمین امن کلیدهای Local/Public و یکپارچه‌سازی ledger با API read-only.  
۳) افزودن آزمون هم‌زمانی، قطع ارتباط و بازیابی با MariaDB واقعی؛ سپس orchestrator idempotent.  
۴) بعد از همهٔ این‌ها، رابط ساده و E2E چندمشتری و فقط سپس بستهٔ واقعی.

## ممنوعیت انحراف
- hardcode دامنه، نسخه، اسم کافه یا مسیر هاست؛ این‌ها فقط دادهٔ ورودی و fixture هستند.
- تفسیر تأیید مالکیت به معنی اجازهٔ قطع اتصال قبلی یا بازکردن سفارش‌گیری مقصد.
- اسکریپت اضطراری یا دستور ویرایش SQL/cPanel برای اپراتور معمولی.
- تغییر سیستم کافه بدون تأیید واقعی نصب پس از آزمون‌های لازم.
- شروع مجدد طراحی و کنارگذاشتن اسناد R251/R252. تاریخچهٔ تصمیم‌ها هرگز پاک نشود.
